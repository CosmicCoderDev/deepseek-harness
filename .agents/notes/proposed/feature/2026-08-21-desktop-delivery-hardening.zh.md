# Agent Note: 桌面版交付加固

Status: proposed

[English](2026-08-21-desktop-delivery-hardening.md) | 中文

## Problem

桌面应用目前已经能够启动、保存设置、显示 Provider 状态并调用 Codex 与 Claude Code，但若干控制仍停留在提示层或尚未贯通。界面上的权限档位并不能单独证明所有 Host 操作都受到上限约束；项目代理偏好还没有完整作用于 Provider 执行链路；文件系统边界需要端到端验证；底层错误对普通用户仍不够可操作；安装后的应用也尚未通过可重复的多 Provider 验收。若在这些边界固定之前继续安装新包，就会得到一个看似完成、实际尚不够安全和易维护的版本。

## Proposal

按顺序完成以下五个桌面版交付阶段。每个阶段都必须保持现有主进程信任边界：渲染器只提交经过校验的操作意图，桌面 Host 负责确定可执行文件路径、Provider 参数、环境变量、权限和文件系统策略。

### 1. 在 Host 强制执行权限上限

将三个桌面权限档位作为可执行的最高权限，而不只是界面标签：

- **只读分析**可以检查所选项目，但不能修改文件、执行会改变状态的命令，也不能绕过审批和沙箱控制。
- **项目开发**可以在所选项目内修改文件并运行普通开发命令，但破坏性操作、特权操作和越界操作仍应被阻止，或进入明确支持的审批流程。
- **完全访问**必须在主进程边界获得明确的二次确认；不能仅凭渲染器值、模型请求、预设或持久化项目策略推导出来。

Host 必须在全局桌面设置、项目策略、任务／会话请求和 Provider 能力之间取最严格的适用值，计算最终有效权限。Provider 原生权限字符串只能在该计算之后生成，属于实现细节。Provider 不得通过提示词、环境变量或子进程参数扩大有效权限。

### 2. 落实项目代理策略

将已保存的代理模式一致地应用于 Host 网络请求和所有 Provider 子进程。支持系统代理、经过校验的手动代理和直连模式；系统代理变化无需重启应用即可刷新；界面显示不含敏感信息的实际生效地址；OpenAI、Anthropic、DeepSeek 和 Ollama 分别测试。

回环地址、`localhost` 和本地 Ollama 服务必须始终绕过外部代理。代理凭据不得进入渲染器状态、日志、诊断信息或复制报告。项目策略可以在允许的模式中选择，但不得注入任意环境变量或 Shell 片段。

### 3. 强制执行读写沙箱边界

每个任务必须绑定到规范化后的项目根目录，并由该目录推导 Provider 工作目录和文件系统授权。授权前必须解析符号链接和路径穿越。只读分析获得只读项目视图；项目开发只能写入经过批准的项目路径和明确管理的临时目录。访问授权根目录以外的位置必须默认拒绝，并返回可操作的错误。

这一约束必须覆盖 Host 直接工具、Codex、Claude Code、Shell 子进程、文件附件，以及所有重连和任务恢复路径。界面徽标和提示词可以解释边界，但不能被视为安全执行机制。

### 4. 提供可操作的诊断与可观测性

将笼统的启动错误和工具错误改为稳定类别及对应处理建议。至少区分：未安装、登录过期、Provider 权限拒绝、代理／网络故障、Host 启动失败、项目策略拒绝、沙箱拒绝、超时、取消和未知异常。

设置页和任务界面应显示 Provider 就绪状态、当前权限档位、实际代理模式、项目根目录、任务阶段和最近一次安全错误。根据场景提供重试、重新登录、连接测试、打开日志目录和一键复制。复制诊断必须限制长度，并在离开主进程前隐藏令牌、OAuth 授权码、代理凭据、邮箱和其他已知敏感信息。

### 5. 执行安装包级桌面验收

验收对象必须是安装后的 macOS 应用，而不仅是源码模式或浏览器页面。验收矩阵覆盖本地 Qwen3 Coder 30B、Codex、Claude Code 以及组合预设，验证 Provider 选择、显式指定 Provider、工具调用成功、真实失败报告、权限阻止、项目根目录隔离、代理切换、localhost 绕过、认证过期、重启／恢复和诊断脱敏。

所有可确定复现的场景都应自动化；浏览器授权等依赖账号的流程保留简短人工清单。子代理调用失败时绝不能显示为已经成功验证的结果。只有验收矩阵通过并确认不存在重复应用包后，新安装包才可以覆盖 `/Applications` 中的版本。

Apple Developer ID 签名、公证和生产级自动更新在获得开发者凭据之前不属于本提案范围。发布说明必须明确这一限制，但不能因此放宽上述五项交付门禁。

## Delivery sequence and dependencies

五个阶段采用有意的先后顺序：

1. Host 权限执行确定后续组件能够获得的最高权限。
2. 代理执行在不破坏本地绕过规则的前提下，建立确定的 Provider 连通性。
3. 沙箱执行把权限约束到具体项目路径和子进程。
4. 诊断界面呈现前三个阶段产生的决策和错误。
5. 安装包验收在用户实际运行的边界验证完整行为。

实现可以拆成多个提交，但不能仅凭界面工作把某一阶段标记为完成。每个阶段都必须在同一变更中增加或更新对应的 Agent Note、测试和用户文档。

## Alternatives considered

**每完成一个可见改进就重新打包安装。** 不采用，因为频繁产生未签名安装包会增加回归和重复安装的辨别成本，而且提示层控制可能在 Host 尚未执行时显得已经完成。

**依赖 Provider 原生权限和提示词。** 不采用，因为不同 Provider 的权限词汇不一致，小型本地模型也可能编造或误用工具；提示词不是安全边界。桌面 Host 必须持有统一权限上限，再映射为 Provider 专用模式。

**先实现诊断，再实现强制控制。** 不采用，因为诊断需要稳定的权限、代理和沙箱结果才能分类。若先做诊断，就会固化临时错误并产生不必要的返工。

**取得 Apple 开发者凭据后再加固。** 不采用，因为签名和公证解决的是分发信任，不解决运行时授权、隔离、连通性和真实失败报告。未签名测试包也应先通过这些门禁。

## Acceptance criteria

- 自动化测试证明渲染器、项目策略、预设、模型请求和 Provider 参数都无法超过 Host 计算出的权限上限。
- 代理设置一致作用于 Host 和 Provider 流量，无需重启即可刷新，能够隐藏凭据，并始终绕过回环地址和 Ollama 流量。
- 只读和项目开发任务在直接工具及两个云端子代理中都被限制在规范化授权根目录内，包括符号链接以及恢复／重连场景。
- 已知失败产生稳定且可操作的分类；脱敏测试证明复制诊断中不包含预先植入的任何敏感信息。
- 安装后的 macOS 应用通过 Qwen、Codex 和 Claude Code 验收矩阵；失败始终以失败呈现，不能触发虚构的回退结论。
- 只有五项门禁全部通过后才向 `/Applications` 安装新版本；签名、公证和自动更新继续明确延期。

## Risks

权限和沙箱的真正执行可能暴露目前依赖宽泛访问才能工作的隐含假设。若没有明确的任务边界，代理刷新可能中断正在执行的任务。Provider CLI 和认证输出可能独立于本仓库变化，因此状态与错误解析需要保守回退。完整安装包验收依赖本地账号和网络状态；依赖账号的场景必须给出明确跳过原因，不能伪装通过。Apple 签名延期意味着测试人员仍会遇到 macOS 对未签名应用的正常信任提示。
